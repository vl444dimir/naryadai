# Покрытие backend интерфейсом НарядAI

Проверка исходного кода: 8 октября 2026 года. Это сверка API, DTO, ролевых условий и доступных действий, а не подтверждение работы на реальных телефонах. После аудита исправлены обнаруженные проблемы и дополнено представление рейтингов/простоев без новых моделей backend.

Источники: [API backend](../backend/app/api/), [schemas.py](../backend/app/schemas.py), [security.py](../backend/app/security.py), [orders.py](../backend/app/services/orders.py), [reports.py](../backend/app/services/reports.py), [App.tsx](src/App.tsx), компоненты [CreateOrder](src/components/CreateOrder.tsx), [OrderDetail](src/components/OrderDetail.tsx), [Reports](src/components/Reports.tsx), [CatalogAdmin](src/components/CatalogAdmin.tsx). Требования сверены с [локальным извлечением кейса](../research/case_extracted.txt).

## Функциональность и роли

«Свои» означает ограничения backend по исполнителю; общий бригадный наряд допускает просмотр задания, а запись результата — одному фактическому исполнителю. «Просмотр» не включает изменение наряда. Руководитель может запросить аналитическое пояснение модели: этот POST не меняет производственные факты.

Служебные маршруты: `/events/stream` не используется — интерфейс работает через авторизованный polling `/events` каждые 2 секунды. `/health` и OpenAPI не являются пользовательскими экранами. Роль admin не исполняет наряд вместо worker; её расширение относится к выдаче, приёмке и управлению справочниками.

## DTO и состояния, проверенные по коду

- Запросы создания, действий, результата, решения, комментария, простоя, отказа, повтора, справочников и смен совпадают со строгими схемами backend. Обязательные `operation_id`/`expected_version`, XOR назначения, timezone дат, версии результата/фото присутствуют. Новых доказанных несовпадений DTO при этой сверке не найдено.
- Числа отчётов приходят с backend; модель пишет пояснение к рассчитанным фактам. `rules` не называется ИИ. Повторы неисправностей сами по себе не снижают оценку без подтверждения мастера.
- Worker не получает в Reports чужие employee/brigade-переключатели; `employee_id` принудительно равен его ID. Полученный пакет дополнительно проверяется по scope, фильтрам и границам периода. Смена пользователя/роли создаёт новый кэш.
- Сетевой сбой сохраняет неопределённую отправку наряда/действия/результата с тем же идентификатором; 409 требует обновления карточки, текст и снимок остаются. После **известного** конфликта фото повтор получает актуальную версию и новый `operation_id`, после **неопределённого** сетевого исхода сохраняет прежний запрос. Автоматической фоновой отправки офлайн-операций нет: повтор явный. Service worker не кэширует `/api` и фото; доступны ранее загруженная оболочка и локальный ввод, а не полная офлайн-база.
- Учётные данные или роль сотрудника отзывают сеанс. При 401 открывается вход; при явном выходе очищаются черновики этого пользователя из **localStorage и sessionStorage**. При истечении сеанса черновики намеренно остаются, что объяснено пользователю.

## Обнаруженные ограничения

1. **Граница персональных оценок.** Свежий `OrderDetail` скрывает чужую оценку по автору события `performed` текущей версии, либо по свежему компактному worker-отчёту. Однако `services/orders.serialize_order` пока передаёт `assessment`, `master_score`, `final_score`, причины/детали событий worker с бригадным доступом. Чужая оценка остаётся в JSON; личный комментарий из события приёмки может попасть в раскрытую историю. UI-маска не заменяет серверную фильтрацию. Нужна проверка каждой исторической версии по её фактическому автору после переназначений.
2. **Масштаб справочников.** `CatalogAdmin` и селекторы рабочих форм читают первую страницу `limit=500`, без перехода к следующим страницам. Смены ограничены последними 200 самим backend. Минимальный набор кейса значительно меньше этих пределов; для большего массива записи за пределами окна недоступны в соответствующих селекторах/списке. Уведомления уже поддерживают следующие страницы и фильтр непрочитанных.
3. **Границы backend и ТЗ.** Анализ фото ограничен метаданными/повторами и проверками заполнения; пиксели «до/после» модели не передаются. Голосовой ввод, чат-ассистент, прогноз отказов и полная офлайн-синхронизация отсутствуют в данном API/этапе. Не заявлять их как реализованные функции интерфейса. Сравнение до/после, звук push и реальные сроки доставки нельзя считать проверенными по наличию кнопок.

## Исправления, учтённые после аудита

- **Фото при 409 исправлено:** `pending.fileData` остаётся в черновике с `versionConflict`, отображается предварительный снимок; обновление карточки сохраняет его, повтор использует новую версию. Эта карточка проверена в общем прогоне **17 DOM-тестов OrderDetail**, включая восстановление снимка и безопасный повтор.
- **Шифр результата исправлен:** сохранённый результат показывает код/название неисправности мастеру и читателю карточки; неизвестная/неуказанная ссылка подписана явно.
- **Рейтинги/простои дополнены:** таблицы показывают итог, пять составляющих, закрытые наряды, доступный вес и статус. Графики исполнителей и бригад имеют шкалу 100; worker не видит чужих строк/графика бригад. Отсутствующие оценки/составляющие/процент простоя остаются прочерком, не нулём.
- **Уведомления дополнены:** все/непрочитанные, `offset` и загрузка более ранних сообщений.

## Доступность и безопасные действия

По коду подтверждены подписи полей, имена иконных кнопок, скрытые декоративные SVG, явные причины/подтверждения, `role=alert/status`, крупные основные действия, native `<dialog>` в карточке, `aria-current` навигации и `aria-pressed` рабочих фильтров. Профиль теперь переносит фокус внутрь, замыкает Tab, закрывается Escape, возвращает фокус; фон помечен `inert`. Временные отметки карточек, уведомлений и topbar приведены к UTC+5. Default master verdict не отправляется автоматически: нужно открытие диалога, ручное сохранение, а при изменении рекомендации — пояснение.

Проверка по коду не доказывает контраст, корректную работу `inert`/диалогов конкретного мобильного браузера, видимость фокуса, работу экранного диктора и отсутствие переполнения на 320–760 px. В CatalogAdmin выбранный раздел пока обозначается CSS без `aria-pressed`; это остаётся ограничением объявления состояния для экранного диктора.

## Фактическая проверка и непроверенные UI

В общем прогоне проекта подтверждены:

- **41 DOM-тест** App, рабочих форм и OrderDetail — успешный прогон, подтверждённый основным процессом разработки. Из них **17** относятся к карточке наряда. Тесты используют jsdom/контролируемые API-ответы, а не настоящую камеру или браузер телефона.
- **10 исходных checks отчётов** — успешно: UTC+5, границы календаря/недели/месяца, shift XOR dates, own worker scope, ошибочные/длинные периоды, отбрасывание чужого/старого пакета, SSR-скрытие enterprise-фильтров.
- **Живой HTTP-прогон через frontend-proxy для четырёх ролей и полного цикла наряда** — успешен по результату основного процесса разработки. Это проверяет реальный backend, авторизацию и прокси, но не клики/рендеринг в браузере.

После добавления таблиц/графика бригад/процента простоя отдельно выполнены:

- `npm run build` — **успешно**: TypeScript и production Vite build.
- `node checks/reports-constraints.cjs` — **14/14**: прежние 10 + SSR-столбцы итог/пять составляющих, график бригад только для руководящих ролей, отсутствие чужой строки у worker, сохранение неизвестных оценок/долей прочерком. Сетевые и модельные вызовы этот скрипт не делает.

**Не проверено:** реальные браузерные экраны и адаптивный вид, камера/галерея/HEIC, сохранение снимка на телефоне, загрузка за 10 секунд, выдача за минуту/6 нажатий, установка PWA/офлайн после перезапуска, фокус native modal на телефоне, реальная Telegram-привязка/звук/доставка, передача модели при production-политике, два-три телефона и конкурентные действия вживую. В CUA нет доступных браузеров; DOM/SSR и HTTP-прокси проверки не заменяют это свидетельство.
