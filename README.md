# НарядAI

Веб-приложение ремонтных нарядов по кейсу АО «Костанайские минералы»: интерфейс React + TypeScript и сервер FastAPI. Мастер выдаёт задания и принимает результаты; исполнитель работает с нарядами, материалами и фотографиями.

Инструкции для интерфейса: [frontend/README.md](frontend/README.md). Общий запуск в подготовленном Windows-окружении: [scripts/Start-NaryadAI.ps1](scripts/Start-NaryadAI.ps1). Ниже описаны сервер и его настройка.

Основной стек: FastAPI, SQLAlchemy 2, PostgreSQL 16, Alembic. Контроль сроков, правила и расчёты выполняет код. Смысловую проверку и текстовые объяснения может выполнять отдельно настроенная модель. Окончательная приёмка всегда за мастером.

## Состав

- Вход по логину с паролем или ПИН, истекающие и отзываемые сессии, временная блокировка неверных попыток, четыре роли.
- Справочники участков, оборудования, сотрудников, бригад, шифров, материалов и нормативов; смены и присутствие сотрудников.
- Полный жизненный цикл наряда, очередь, отказ и пауза с причинами, переназначение, отмена и изменение приоритета или срока.
- Проверка версии, идемпотентные операции и атомарный журнал; конкурентное принятие и ограничение одной активной работы на человека.
- Версии результатов, материалы, фотографии JPEG/PNG/WebP, сжатие, защищённая выдача, проверка одинаковых и похожих файлов.
- Сохраняемая очередь проверки результатов; модельный адаптер, проверка ответа и его ссылок, повторные попытки и ручная проверка при недоступности модели.
- Напоминания, просрочки, непринятие аварийного и обычного наряда, длительная эскалация руководителю; локальный список уведомлений и Telegram с подтверждением владельца чата.
- События через SSE и запрос изменений по курсору; восстановление актуального состояния после переподключения.
- Отчёты по наряду и периоду, рейтинг исполнителей и бригад, материалы, подтверждённые простои, сигналы истории и XLSX.
- Генератор 582 демонстрационных нарядов, обязательных справочников и четырёх закономерностей за 90 дней.

## Локальный запуск в Windows

Python 3.12+, PostgreSQL 16, права администратора и перезагрузка для запуска приложения не нужны. Команды выполняются из корня проекта. В подготовленном окружении `.venv` и локальная `.env` уже существуют; пароли и файлы базы исключены из Git.

Для новой машины установите зависимости и задайте подключение к отдельной базе в `backend/.env`:

```powershell
uv venv --python 3.12 .venv
uv pip install --python .venv\Scripts\python.exe -r backend\requirements.txt
Copy-Item -LiteralPath backend\.env.example -Destination backend\.env
```

Копирование примера предназначено только для новой машины без существующей `.env`: не заменяйте подготовленные настройки. В `DATABASE_URL` укажите действительную базу и её пароль. Миграции меняют только схему выбранной базы, поэтому перед выполнением проверьте адрес подключения.

```powershell
Set-Location backend
..\.venv\Scripts\alembic.exe upgrade head
..\.venv\Scripts\python.exe -m app.seed
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Генератор вызывается явно. Он добавляет демонстрационные записи, не удаляет данные и не перезаписывает существующие пароли или пользовательские изменения. Для проверенных неизменённых записей собственного демонстрационного набора заполняет отсутствующие исторические снимки из первоначального состава бригад; текущая бригада сотрудника не используется для прошлого. При конфликте демонстрационного ID с чужой записью загрузка прекращается.

Во втором терминале, также из папки `backend`, запустите обработчик сроков, проверок и доставки:

```powershell
..\.venv\Scripts\python.exe -m app.worker
```

Документация: [Swagger](http://127.0.0.1:8000/docs). Состояние: [health](http://127.0.0.1:8000/health). Остановка каждого процесса — Ctrl+C в его терминале.

Тестовые логины: `demo.master1`, `demo.master2`, `demo.worker01`–`demo.worker15`, `demo.leader`, `demo.admin`. Пароль задаётся `DEMO_PASSWORD`, значение примера — `Demo-Only-2026!`. ПИН появляется только после отдельного назначения администратором; приложение не создаёт общий ПИН автоматически. Демонстрационные аккаунты предназначены для отдельного стенда с тестовыми данными.

## Docker Compose

На машине с работающим Docker Desktop задайте случайный `POSTGRES_PASSWORD` в корневой `.env`, создайте `backend/.env` из примера и настройте ИИ/Telegram при необходимости. База и фото хранятся в отдельных томах. Сначала выполните миграции; генератор данных вызывается отдельно.

```powershell
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose run --rm api python -m app.seed
docker compose up -d api worker
docker compose logs --tail 50 api worker
```

API публикуется на `127.0.0.1:8000`. Для завершения используйте `docker compose stop`; тома с данными сохранятся. Docker-конфигурация проверяется командой `docker compose config --quiet`. Фактическая сборка контейнеров на текущем устройстве не подтверждена: при проверке Docker Desktop завершил запуск engine с ошибкой служебного сокета `sailor-ingest.sock`. Нативный запуск Python/PostgreSQL проверен.

## Подключение клиента

Все прикладные маршруты имеют префикс `/api`. Вход: `POST /api/auth/login` с JSON `{"login":"...","password":"..."}` либо `{"login":"...","pin":"..."}`. Клиент передаёт `Authorization: Bearer <access_token>`; выход отзывает сессию.

Для создания и изменения наряда клиент генерирует `operation_id` как UUID. Изменение также передаёт `expected_version` из последнего ответа. Повтор той же операции возвращает сохранённый результат. Другие данные с тем же ID или устаревшая версия дают 409. В этом случае клиент сохраняет черновик и перечитывает карточку.

Основные маршруты:

| Задача | Маршрут |
| --- | --- |
| Справочники и люди | `/api/catalog/*`, `/api/catalog/users` |
| Создать, найти, прочитать, изменить | `/api/orders`, `/api/orders/{id}` |
| Принять, очередь, отказ, начало, пауза, продолжение | `POST /api/orders/{id}/actions` |
| Загрузить фото | `POST /api/orders/{id}/photos`, multipart с operation_id, expected_version, kind, file |
| Представить результат | `POST /api/orders/{id}/result` |
| Решение мастера | `POST /api/orders/{id}/decision` |
| Простой, комментарий | `/api/orders/{id}/downtime`, `/api/orders/{id}/comments` |
| Обоснованность отказа, подтверждённый повтор | `/api/orders/{id}/rejection-decision`, `/api/orders/{id}/confirm-repeat` |
| Уведомления | `/api/notifications`, `/api/notifications/status` |
| Обновление открытого экрана | `/api/events?after=<cursor>`, `/api/events/stream?after=<cursor>` |
| Карточка отчёта | `/api/reports/orders/{id}` |
| Смена и произвольный период | `/api/reports/shift`, `/api/reports/ratings`, `/api/reports/materials`, `/api/reports/downtime`, `/api/reports/anomalies` |
| Текстовая модельная сводка | `POST /api/reports/summary` |
| Объяснение рейтинга | `POST /api/reports/ratings/{employee_id}/explanation` |
| Excel | `/api/reports/export.xlsx`, `/api/reports/orders/{id}/export.xlsx` |

Типы тел запросов доступны в OpenAPI. Время передаётся в ISO 8601 с часовым поясом. Отчёт принимает `from_at` и `to_at` либо `shift_id`, а также фильтры `section_id`, `equipment_id`, `employee_id`, `brigade_id`. Период полуоткрытый: начало включается, конец не включается. День по умолчанию считается в UTC+5.

SSE требует Bearer в заголовке: используйте потоковый `fetch`, а не передачу токена в URL. Альтернатива — запрос `/events` раз в две секунды. По событию клиент перечитывает соответствующий наряд. При восстановлении соединения загружается актуальный снимок. Фактические 5 секунд на телефонах проверяются отдельно.

При `action=assignment_revoked` клиент убирает наряд из списка и закрывает его карточку. Это адресованный сигнал прежнему исполнителю после переназначения; он содержит ID и время, без нового статуса и пояснения мастера. Дальнейшие события и карточка чужого задания ему недоступны.

## ИИ и фотографии

По умолчанию `AI_ENABLED=false`. Проверка полей и времени работает, но `engine=rules`, `score=null`; мастер задаёт оценку вручную. Исторические оценки генератора имеют `engine=seed`. Эти режимы не обозначаются как вызовы ИИ.

Для модели задайте `AI_ENABLED=true`, `AI_PROVIDER=openai` или `ollama`, `AI_BASE_URL`, `AI_MODEL`, для внешнего API также `AI_API_KEY`. Для Ollama адрес обычно `http://127.0.0.1:11434`, а имя модели должно действительно присутствовать в локальном сервисе. Проверка текстов использует Chat Completions совместимый JSON-контракт и проверяет результат на сервере. [Официальный формат API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), [структурированные ответы](https://developers.openai.com/api/docs/guides/structured-outputs).

Новые наряды из API по умолчанию не считаются синтетическими даже при входе демонстрационным аккаунтом. Вызов модели для них блокируется, пока администратор отдельно не включит `AI_ALLOW_REAL_DATA`; этот флаг требует согласованного состава данных. Имена известных сотрудников, телефоны и email удаляются из текстов, но автоматическое удаление не гарантирует обезличивание любого свободного текста. История генератора синтетическая. Сводка и объяснение рейтинга передают только разрешённые числовые показатели.

Настройте провайдера до представления новых результатов. Сохранённая проверка предыдущей версии остаётся в истории; повторная отправка после доработки создаёт новую версию и новую проверку. Модель рекомендует вердикт, программа сохраняет обязательные замечания, мастер закрывает наряд. После трёх неудачных попыток результат не теряется и предлагается ручная проверка.

В этом этапе фото проверяются базово: наличие, заявленное время, точное совпадение SHA-256 и сходство dHash 8×8. Фото уменьшается до 1600 px по длинной стороне и JPEG; клиент должен заранее уменьшать исходник для быстрой мобильной загрузки. EXIF, время телефона и похожесть не доказывают фактическую свежесть или техническую исправность. Пиксели во внешнюю модель не отправляются; полное мультимодальное сравнение пока не реализовано.

## Уведомления

Укажите `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и `PUBLIC_APP_URL`, затем запустите worker. Пользователь получает одноразовую ссылку через `POST /api/notifications/telegram/link` и открывает её в Telegram. Привязка завершается только после сообщения боту из личного чата. Произвольный chat ID через API не принимается. `PUT /api/notifications/telegram` с `{"chat_id":null}` отвязывает чат.

Обработчик использует `getUpdates`; у этого бота не должен одновременно работать другой потребитель обновлений или webhook. Отправка сохраняется в очереди, повторяется при сбоях и доступна для диагностики через собственный список пользователя. Внешняя отправка для реальных нарядов содержит краткое уведомление и ссылку, подробности остаются в приложении. Неопределённый сетевой таймаут может привести к повторной доставке Telegram, поэтому внешняя доставка имеет семантику «не менее одного раза».

Контроль сроков, вызовы модели и внешняя доставка выполняются отдельными циклами. Пороги примера: 30 минут до срока, 10 минут до эскалации непринятого задания, 3 минуты для аварийного, повтор через 30 минут и руководителю через 120 минут просрочки. Звук определяется устройством и Telegram; его нужно проверить на настоящем телефоне.

## Расчёты

Просрочка вычисляется поверх стадии наряда. После представления результата контроль исполнения останавливается, после возврата возобновляется; изменение срока мастером записывается. Своевременность учитывает отправку принятой версии, ожидание мастера не является задержкой исполнителя.

Смена задаёт временной интервал отчёта и учитывает переходящие работы независимо от смены выдачи. Состав из `ShiftMember` возвращается отдельно; фактическая работа сотрудников вне состава явно отмечается. `GET /api/orders` возвращает `total`, `counts_by_status` и `overdue_count` по всем доступным строкам с выбранными фильтрами, независимо от страницы.

Бригада выдачи сохраняется в снимке назначения; закрытые работы и материалы относятся к бригаде автора принятой версии результата; интервалы работы и отказы — к снимкам событий. Перевод сотрудника или изменение его роли не переписывают прошлую атрибуцию. Для старых реальных записей без снимков историческая бригада отмечается как неизвестная, без подстановки текущего состава.

Простой фиксируется явными действиями start/end и причиной; пересекающиеся интервалы одного оборудования объединяются. Время активной работы берётся из переходов начала/паузы/продолжения/исполнения. Оно отдельно от ожидания и простоя.

Отмена или приёмка наряда не означают восстановление оборудования. Уже открытый простой можно явно завершить и после отмены или закрытия; новый простой в завершённом наряде начать нельзя.

Рейтинг: 40% качество Q, 25% своевременность T, 15% приёмка с первого раза F, 15% нормативный объём C, 5% обоснованность отказов A. Q — средняя оценка 1–5 / 5; T — доля закрытых работ, сданных в срок; F — доля без доработки и подтверждённого повтора среди работ с полным семидневным наблюдением; C — закрытые нормативные минуты / назначенные нормативные минуты; A использует подтверждённые мастером отказы. Отсутствующие компоненты отмечаются, балл предварительный. Составляющие, веса, знаменатели и исходные наряды возвращаются вместе с результатом. Автоматически найденная связь отказов не доказывает вину работника.

## Проверки

Из папки `backend`, для тестов создайте новую отдельную временную папку в пределах проекта:

```powershell
$taskTestRoot = Join-Path (Get-Location) ('..\.local\pytest-' + [guid]::NewGuid().ToString('N'))
..\.venv\Scripts\python.exe -m pytest -q --basetemp $taskTestRoot
..\.venv\Scripts\alembic.exe check
```

Сквозной smoke выполняется **только на отдельном локальном демонстрационном стенде** с запущенным API, добавляет тестовые наряды и проверяет просрочку:

```powershell
$env:PYTHONPATH = (Get-Location).Path
..\.venv\Scripts\python.exe scripts\smoke_postgres.py
```

После настройки модели её живую проверку можно запустить отдельно. Скрипт не читает базу: отправляет шесть синтетических примеров и одну числовую сводку, проверяет смысловые несоответствия, отсутствие фото, точный повтор и попытку подменить инструкции. Без `--run` или настроенного провайдера запросы не выполняются.

```powershell
$env:PYTHONPATH = (Get-Location).Path
..\.venv\Scripts\python.exe scripts\verify_model.py --run
```

Результат сохраняется в `backend/.local/model_validation.json`. Это небольшой приёмочный набор для интеграции; он не доказывает точность модели на всех ремонтах или качество ремонта по изображению.

Текущее подтверждение проверки и оставшиеся внешние условия записаны в `backend/VALIDATION.md`, соответствие пунктам ТЗ — в `backend/REQUIREMENTS.md`. Мобильное удобство, число нажатий, фактическая доставка со звуком и качество живой модели проверяются на следующем интеграционном этапе. Для этих пунктов одного backend недостаточно.
